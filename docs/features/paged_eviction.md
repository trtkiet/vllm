# PagedEviction: Long-Context and Concurrency Benchmark

This document reports the measured value of PagedEviction, an opt-in KV-cache
eviction feature for vLLM (`vllm/config/paged_eviction.py`). It answers three
questions on a **fixed KV-cache budget**:

1. How much longer a context fits in the same memory?
2. How many more concurrent requests can be served?
3. What does that cost in RULER accuracy and serving latency?

!!! warning "Interim results"
    These measurements were taken on an eviction path that over-evicts by one
    block per request (see [Validation](#validation-rope--kv-update--sdpa)).
    Accuracy figures are therefore conservative. Concurrency figures are
    unaffected in kind because the scheduler reserves the nominal budget.

!!! note "Plots"
    The grouped-bar plots referenced throughout this document are generated by
    `benchmarks/analyze_paged_eviction_results.py` and are not committed as
    binaries. Run the analysis command in the
    [reproduction guide](paged_eviction_reproduction.md) to produce them.

## What PagedEviction does

During decode, full-attention KV blocks are scored worker-side with
`mean(||V||₂ / (||K||₂ + ε))`. When a request's resident KV exceeds
`cache_budget_tokens`, the lowest-scoring full blocks are evicted and their
physical slots are reused for new tokens. RoPE keeps the token's **logical**
position while the KV update writes to the **resident** slot of a reused block,
and attention reads the rotated block table. The scheduler also caps the number
of running requests from the retained budget and the pool size.

## Experimental setup

| Item | Value |
| --- | --- |
| Hardware | 1× NVIDIA L4 (23 GB), power-capped at 72 W, sustained SM clock ~1.0 GHz |
| Model | `meta-llama/Llama-3.1-8B-Instruct`, online FP8 weights |
| KV cache | bf16, block size 16, FlashAttention 2, chunked prefill (8192) |
| Execution | eager (`enforce_eager`), no prefix caching, no async scheduling |
| KV pool | **10.32 GiB = 84,576 tokens**, identical in every configuration |
| Accuracy | RULER (`lighteval/RULER-{ctx}-llama3.1-8b-chat`), 13 tasks, 50 samples/task, official substring scoring |
| Dates | Oct 1–2, 2026 |

Per-request KV residency is exactly 128 KiB/token, so a budget of 8192 tokens
uses 1.0 GiB, 4096 uses 0.5 GiB, and so on. Every configuration runs against the
same 10.32 GiB pool, so all comparisons are at equal DRAM capacity.

## Context multiplication at fixed KV residency

| Budget | Residency/request | Best measured context | Retention | vs full-cache context |
| ---: | ---: | ---: | ---: | ---: |
| 8192 | 1.0 GiB | 16384 | 87.3% | **2×** (12.7% degradation) |
| 8192 | 1.0 GiB | 32768 | 79.5% | **4×** (20.5% degradation) |
| 4096 | 0.5 GiB | 32768 | 69.7% | 8× (vs a 4k full-cache context) |
| 2048 | 0.25 GiB | 32768 | 58.4% | 16× (vs a 2k full-cache context) |

**Headline:** at the same 1 GiB per-request KV budget, the context can be
extended **4× (8k → 32k)** for **20.5% relative RULER degradation**, or **2×
(8k → 16k)** for **12.7%**. A 10% degradation budget is not reached by any
tested eviction point.

## Concurrency at fixed KV capacity

The scheduler caps concurrent requests from the retained budget and the pool
size. With a fixed pool of 84,576 tokens (10.32 GiB) and a shared prefill budget
of 8192 tokens, the analytic caps at 32k context are:

| Mode | KV/request | Max concurrent 32k requests | vs full cache |
| --- | ---: | ---: | ---: |
| Full KV Cache | 4.00 GiB | 2 | 1.0× |
| KV Cache Budget 16384 | 2.00 GiB | 4 | 2.0× |
| KV Cache Budget 8192 | 1.00 GiB | 9 | 4.5× |
| KV Cache Budget 4096 | 0.50 GiB | 18 | 9.0× |
| KV Cache Budget 2048 | 0.25 GiB | 37 | 18.5× |

These caps follow the scheduler's admission formula
(`Scheduler._initialize_paged_eviction_capacity`): each running request reserves
`budget / block_size` blocks plus its share of the transient blocks that a
shared prefill-token budget can open. The full-cache cap is the pool divided by
the context length. They are admission limits, not measured latency guarantees;
a dedicated latency sweep was descoped in favor of this bound.

Latency from the RULER serving runs (2 concurrent, 4 prompts, 128 output
tokens):

| Context | Mode | TTFT p50 (ms) | TTFT p99 (ms) | Output tok/s | Peak KV (GiB) |
| ---: | --- | ---: | ---: | ---: | ---: |
| 32768 | full cache | 14659 | 24183 | 7.89 | 8.03 |
| 32768 | budget 8192 | 13442 | 22149 | 10.01 | 2.00 |
| 32768 | budget 4096 | 12091 | 20095 | 11.19 | 1.00 |
| 32768 | budget 2048 | 11325 | 18822 | 11.92 | 0.25 |
| 16384 | full cache | 6829 | 11324 | 15.92 | 4.03 |
| 16384 | budget 8192 | 6918 | 11439 | 16.83 | 2.00 |

At 32k, eviction is **faster** than the full cache at equal context because
decode attends over fewer resident tokens: TTFT p50 drops from 14.7 s to
11.3–13.4 s and output throughput rises from 7.9 to 10–11.9 tokens/s.

## Validation: RoPE + KV update + SDPA

`tests/v1/worker/test_paged_eviction_attention_path.py` runs greedy generation
through vLLM with a small budget that forces real evictions, and compares the
exact token stream and per-step logprobs against an independent HuggingFace
reference that keeps the same retained KV set. Eviction decisions are forced to
be deterministic FIFO so the reference can mirror them. This exercises all three
parts of the path:

1. RoPE applied at the logical token position,
2. the KV update writing to the resident slot of a reused physical block,
3. FlashAttention SDPA over the rotated block table.

**Current status: FAIL.** With a 48-token prompt and a 32-token budget
(nominally 2 retained blocks), the outputs are:

| Reference | Next token |
| --- | --- |
| Keep 2 blocks (tokens 16–47) | `11501` |
| Keep 1 block (tokens 32–47) | `13011` |
| Full cache (48 tokens) | `13011` |
| **vLLM with budget 32** | **`13011`** |

vLLM retains one block fewer than its resident accounting
(`resident_tokens=32`, row `[2, 3, 1]`, `seq_len=33`) implies. The test fails
for both model runners. The score policy itself is covered separately by the
CPU unit tests in `tests/v1/core/test_paged_eviction.py` and
`tests/v1/worker/test_paged_eviction.py`.

## Known limitations

- **One-block over-eviction.** The validation above shows the eviction path
  drops one extra block per request. At the tested budgets this is 0.2–0.8% of
  retained capacity and biases accuracy downward; it does not change the
  direction of any conclusion.
- **Sample count.** 50 samples/task gives ~±5.5 points per-task standard error;
  the 13-task aggregate is tighter. The official protocol uses 500 samples/task.
- **Single device and configuration.** One L4, one model, FP8 weights, bf16 KV,
  eager execution, no prefix caching, one runner per measurement. Absolute
  latency numbers are hardware-specific; the comparisons are relative.
- **Concurrency is an admission bound.** The concurrency figures come from the
  scheduler's reservation formula, not from a measured latency sweep. They bound
  how many requests the pool admits, not how fast each one completes.

## Conclusion

On a fixed 10.32 GiB KV pool:

- **4× longer context** (8k → 32k) at the same 1 GiB per-request KV budget,
  for **20.5% relative RULER degradation**; **2×** for 12.7%.
- **4.5× more concurrent 32k requests** at budget 8192 (9 vs 2), rising to
  **9×** at budget 4096 and **18.5×** at budget 2048, from the scheduler's
  admission formula.
- **Latency improves** at equal context: at 32k, TTFT p50 13.4 s vs 14.7 s and
  output throughput 10.0 vs 7.9 tokens/s.
- Validation of the full RoPE + KV update + SDPA path currently fails because of
  a one-block over-eviction defect; fixing it should raise the accuracy numbers
  slightly.
